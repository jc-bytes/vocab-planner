# Active student attempt runtime

`StudentActivityProgressPersistence` retains the normalized result processor, in-memory sync-state registry, debounce configuration, owner reset, reward values and state-value validation. The durable queue remains independently available. Queue replay applies results through this eager boundary, including its `preserveLocalState` and `localStates` options. Flush, pagehide, visibility changes and unused timer APIs do not load an engine.

The real activity launcher explicitly awaits `prepareActiveRuntime` before verification and activity construction. `studentActiveRuntime.js` owns AttemptService, AutoSave, StateStore, SyncCoordinator and WorkTimer. The bounded preparation lease captures account, school, unit, cloud session and launch ownership. Reset aborts a held preparation synchronously. An ignored or failed import cannot install a stale engine; a timed-out import permits a fresh retry. The normal same-user auth refresh retains the existing initialized owner and remains valid. Existing routing cancellation also ends held startup immediately, including navigation away and back to the same hash. The parent route checks its captured navigation after vocabulary preparation; it cannot start obsolete work under a newer route. The launcher owns Illustration word normalization and renews its lease only for its own current word-route writes, preserving live saves without reviving externally cancelled work.

The engine is retained after normal activity cleanup. Its sync-state Map therefore keeps pending, unsaved and in-flight receipts across activity and unit navigation. Session reset clears that registry and disposes the timer. A completed old attempt still applies its authoritative result and persistence acknowledgement, but cannot finish a replacement activity's timer or display its XP completion UI.

Teacher preview installs its own verification and write overrides on the eager persistence object. Explicit engine preparation remains required in this path and does not overwrite those methods. Constructors can synchronously call progress and state callbacks once preparation succeeds.

Verification uses `tests/student-active-runtime.test.mjs`, the retained write-reduction/runtime-composition suites, and launcher recovery controls. `test:ui:student-active-runtime` runs the real app with synthetic network fixtures; `UI_STUDENT_RUNTIME_DIST=1` selects the built app. The browser gate blocks service workers to measure application import requests: Home, Units, Sparks and Arcade leave the engine unloaded; an actual activity imports it once. The offline worker still intentionally precaches the complete supported graph in the background. This extraction changes initial execution and requests, not that offline policy.

The coordinated production build measures 208,246 initial student JS/CSS gzip bytes (level 9), down 4,907 bytes from 213,153, under the unchanged 215,040-byte limit. Teacher initial delivery is 168,888 bytes, compared with 168,878 before this change. The active engine's retained dynamic chunk is 7,512 gzip bytes; its gross chunk size is not the net startup saving.

Built browser controls pass for all five cold views, explicit launch, actual teacher iframe preview, immediate-release and still-held import cancellation, same-hash replacement, and missing-engine recovery before verification or construction. Actual Illustration controls canonicalize an invalid word, dismiss the native first-visit guide, change words and save through real callbacks; old callbacks cannot rewrite Home or save after navigation. With service workers blocked and network idle reached, observed emitted JS/CSS requests are Home 40 (237,812 gzip bytes), Units 40 (236,755), Sparks 41 (242,809), Arcade 42 (261,685), and Flashcards 44 (268,139). These totals include the data and presentation modules each route actually loads, beyond its static entry graph. The first four request zero active-engine modules; Flashcards requests one. Actual local authenticated startup controls also pass transient verification, denial, activity-module, stylesheet, launcher and request-module failures in source and built modes. No hosted or physical-device claims follow from these local controls.
